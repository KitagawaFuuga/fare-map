# 0001: main は CI が通った変更だけを受け付ける

- 日付: 2026-11-15
- 状態: 採用

## 背景

main への push がそのまま本番デプロイになる（`.github/workflows/deploy.yml`）。
一方で main には保護がなく、CI が落ちていてもマージでき、直接 push もできた。
これまでは人がマージの判断をしていたので問題にならなかったが、実装からマージ
までを AI に任せる範囲を広げると、検査を通っていない変更が公開される経路が残る。

## 選択肢

- 案A: 保護しない。運用で気をつける。手間はないが、AI が手順を飛ばしたときに
  止めるものがない
- 案B: CI（`test` と `e2e`）の成功を必須にする。管理者にも適用する。
  直接 push できなくなり、すべての変更が PR を通る
- 案C: 案B に加えてレビューの承認を必須にする。1人で開発しているので、
  自分の PR を承認できずマージできなくなる

## 決定

案B。止めたいのは「検査を通っていない変更が main に入ること」で、それは
CI の必須化で足りる。管理者にも適用するのは、AI がユーザーの権限で操作する
ため、管理者を例外にすると保護が効かないから。

main が最新の状態で検査されていること（strict）も必須にした。別々に通った
2つの PR が、合わせると壊れる場合を防ぐ。

## 結果

- 変更はすべて PR 経由になり、PR の説明が開発の履歴になる
- 文書だけの修正でも CI を待つ（3分程度）
- Dependabot の PR は、他の PR をマージするたびに rebase が要る
