# 0003: 新しい版は確かめてから本番に流す

- 日付: 2026-11-22
- 状態: 採用
- 決めた人: ユーザー（AI が出した3案から選んだ）

## 背景

デプロイは `az containerapp update` で新しい版を作り、その時点で利用者の流れが
100% そちらへ移っていた。デプロイ前の E2E（0002）が見ているのは `npm run build`
の成果物で、本番に出す Docker イメージそのものは API 1本のスモークテストしか
通らない。イメージにしかない不具合（standalone サーバーでのワーカーの 404 など）は、
利用者が開いて初めて分かる状態だった。

## 選択肢

- 案A: 出してから確かめる。切り替えたあとに本番 URL を確認し、だめなら前の
  イメージに戻す。今の構成のまま足せるが、戻すまでの1〜2分は壊れた版が見える
- 案B: 確かめてから出す。新しい版を流れ 0% で起動し、その版専用の URL に E2E を
  かけ、通ったら切り替える。壊れた版は利用者に見えないが、Azure の設定を
  複数リビジョンのモードに変え、手順が増える
- 案C: 確かめて知らせるだけ。戻すのは人の手。全自動の目的に合わない

## 決定

案B。開発を AI に任せる範囲を広げると、壊れた版に気づく人がいない。気づいて
戻す前提の案A より、利用者に届く前に止める案B が合う。

E2E は `e2e/smoke.spec.ts` のうち `@prod` を付けた3本だけを流す（地図とワーカー、
検索で駅が出るか、範囲外の駅で地図が動いて円が描かれるか）。本番のレート制限は
1つの IP につき20回で、全部流すと当たるため。

## 結果

- 失敗したら新しい版を止めて終わる。利用者は前の版のまま
- `latest` タグは切り替えのあとに付ける。確認に落ちた版が `latest` にならない
- デプロイがさらに数分遅くなる（0台からの起動待ちと E2E）
- 本番が0台まで縮む設定なので、新しい版の初回の応答は遅い。手元で本番に向けて
  流したとき、1回目だけ3本中2本がタイムアウトした（2回目以降は通った）。
  workflow では駅の候補が返るまで待ってから E2E を始める
- 手元から Azure の設定を変えて試すことはしていない。最初のデプロイが、
  この手順の最初の実行になる。そこで落ちても、固定した前の版に流れたままになる
