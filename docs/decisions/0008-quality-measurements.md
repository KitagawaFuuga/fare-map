# 0008: アクセシビリティ・表示速度・DORA の指標を測る

- 日付: 2026-11-25
- 状態: 採用
- 決めた人: ユーザー（AI が出した案から、それぞれの扱いを選んだ）。使う道具の版と、指標の細かい定め方は AI の判断

## 背景

テストは「動くか」を確かめていたが、次の3つは測っていなかった。

- 画面が誰にでも使えるか（アクセシビリティ）
- 画面がどれだけ速く出るか（Core Web Vitals）
- 開発の流れがどれだけ速く、安定しているか（DORA の指標）

## 選択肢

- アクセシビリティ（axe を E2E に組み込む）: 案A serious・critical だけ CI を止める / 案B 全部で止める / 案C 報告だけ
- 表示速度（Lighthouse CI）: 案A PR ごとに測って警告だけ / 案B PR ごとに測って止める / 案C 本番を週1回測る
- DORA: 案A 月1回自動で集計して実行の要約欄に出す / 案B 手で流すスクリプトだけ / 案C 集計結果を docs にコミットする PR を毎月作る

## 決定

- アクセシビリティは案A。`e2e/a11y.spec.ts` が、開いた直後の画面（デスクトップとスマホ）と検索結果の画面（デスクトップ）を
  WCAG 2.2 AA までのルールで検査する。moderate・minor は結果に添付するだけ。
  入れた時点の違反は、出典の文字のコントラスト不足（`text-gray-400`、白地で約 2.6:1）の1件だけで、`text-gray-500` に直した
- 表示速度は案A。CI はぶれるので止めない。`lighthouse` ジョブは必須のチェックにもしない。結果は外部の公開ストレージに上げず、
  ジョブの要約欄の表（`scripts/analysis/lighthouse-summary.ts`）と artifact のレポートで見る。
  INP は操作しないと測れないので、実験室での代わりに TBT を見る
- DORA は案A（`.github/workflows/dora.yml`、毎月1日）。5つの指標の定め方は `scripts/analysis/dora-metrics.ts` の冒頭に書いた。
  dora.dev は時刻の始まりと終わりや集計のしかたまでは決めていないので、このリポジトリで取れる記録（デプロイの成功、
  コミット、revert）に合わせた
- 道具の版は固定した（`@axe-core/playwright` 4.14.0、`@lhci/cli` 0.16.1）。最新の 4.14.1 は公開の翌日だったので見送った

## 結果

- 本番の障害を revert ではなく修正で直したときは、コミットのメッセージに `[incident]` を付ける。付けないと手戻りに数えられない
- DORA の数字は目標にしない（dora.dev: 目標にすると数字がゆがむ）。前の月との違いと理由を話す材料にする
- 入れた時点の手元の Lighthouse は、スコア 67・LCP 1.25 秒・CLS 0.028・TBT 5.6 秒。TBT が基準（200ms）を大きく超えていて、
  地図の初期化が遅いスマホの CPU で重いのが原因とみている。直すのは別の課題
- `@lhci/cli` で開発用の依存が 254 個増えた。`npx` で毎回取ってくると中の版が固定されないので、lock ファイルで固定する方を選んだ
