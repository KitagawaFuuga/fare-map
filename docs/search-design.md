# 到達可能駅探索の設計メモ

`lib/search/reachable.ts` の設計判断のうち、コード中のコメントに収めると長くなる
導出過程をここに置く。コード側からはこのファイルを参照している。

## 1. Pareto 支配の次元をどう決めたか

### なぜ「今の運賃が安い方を残す」ではダメか

特定運賃（override）は駅ペア単位で効くため、今この駅で降りた場合の運賃は距離について
単調にならない。「今安い状態」だけを残すと、いま高いが先の駅で override により安くなる
経路を取りこぼす。そこで `(confirmedFare, 距離)` の非支配集合（Pareto 集合）を保持する。

### 4次元に落とすまで

当初は `segmentKm` と `honshuThroughKm` を別々の次元として持っていたが、次の理由で
両者の和（`totalKm`）に射影できる。

- 同一 bucket 内では `segmentOperator` / `segmentOnlyExcludedLines` /
  `segmentOriginInTokyoArea` が全エントリで共通（すべて bucket キーの一部）。
  よって `segmentEastKmContribution` は「bucket の終端駅と `segmentKm`」だけの関数になり、
  bucket 内では常に「0固定」か「`segmentKm` 固定」のどちらかに定まる。
  運賃計算（`estimateHonshuThrough` / `honshuThroughBaseFare`）はどちらも
  距離の和にしか依存しないので、内訳を個別に持つ必要がない。
- `isHonshuThrough === false` の bucket では `honshuThroughKm` / `honshuThroughEastKm`
  は常に 0 なので、比較結果は従来と変わらない。
- `isHonshuThrough === true` の bucket では、和だけを比較する方が**真に強い支配**になる。
  例: `segmentKm=0, honshuThroughKm=10` と `segmentKm=10, honshuThroughKm=0` は
  総距離が同じ 10km で運賃も完全に同一だが、内訳を別次元にしていた頃は
  互いに非支配のまま両方残っていた。

### pendingEastKm を足した理由（レビュー指摘）

「bucket 内では 0固定 か segmentKm固定 のどちらかに定まる」は*今この瞬間の*
`totalEastKm` については正しいが、「0固定」の bucket では、
`segmentOnlyExcludedLines` のラチェットが将来落ちた瞬間に「segmentKm固定」へ
切り替わりうる。そのとき加算されるのは隠れていた `segmentKm` そのものなので、
`(confirmedFare, totalKm, totalEastKm)` だけでは「将来不利な状態」と
「将来有利な状態」が完全に同一に見えてしまう。

そこで `pendingEastKm = totalEastKm + (0固定で隠れている場合の segmentKm)` を
4次元目として非 strict に比較する。「segmentKm固定」の bucket
（`isHonshuThrough === false` を含む＝実データの96%以上）では `totalEastKm` と
常に一致する冗長次元になり、比較結果にも性能にも影響しない。

現在のデータでは該当 bucket が空で到達しないことを実測で確認済みだが、
グラフ再生成で新幹線データが加わると容易に到達しうる潜在的な不健全性だった。

### 支配の向き

`segmentKm` は**小さいほうが有利**。この向きを逆にすると、同じ路線を往復するだけで
`segmentKm` が単調増加する状態が永遠に非支配のまま生成され続け、探索が停止しない。

## 2. 加算額の除外区間（東京〜熱海）

### 規則

「東京都区内・山手線内から東海道方面へ通し運賃で乗る場合、東京(品川)〜熱海間は
東海道新幹線（JR東海）経由として計算されるため、この区間の JR東日本分の加算額は
発生しない」（出典: https://ameblo.jp/yyrapid/entry-12937999551.html ）。

グラフに新幹線データが無いため、対応する在来線区間の lineId
（JR東海道本線 東京〜熱海 = `11301`、JR山手線 = `11302`）を目印に使う。
除外するのは加算額の対象キロ（eastKm）だけで、総営業キロ（`totalKm`）は
実際の経路の距離のまま変えない。

### 修正した2つのバグ

**過小評価（起点・終端の適格性を見ていなかった）**
当初は両端ノードの lineId だけを見ており、乗車が東京都区内・山手線内発着かを
一切見ていなかった。lineId `11301`（21ノード）には戸塚・大船・藤沢・平塚・小田原・
湯河原・横浜など、東京都区内でも山手線内でもない駅が多数含まれる。そのため
「小田原→熱海(JR東日本)→(JR東海)」のような経路でも除外が発動し、JR東日本区間の
加算額が丸ごと0円になっていた。`isEligibleExclusionName` で
「区間の起点または終端が東京都区内・山手線内の駅か」を追加の必要条件にして解決。

**上り方向の非対称（起点しか見ていなかった）**
適格性を「区間の起点」だけで判定していたため、上り（例: 名古屋→東京）では
会社境界の熱海が起点になり、山手線名集合に入らず除外が発動しなかった。
実運賃は方向対称のはずなのに、上りだけ加算額が誤って上乗せされていた。
区間の「終端」も判定対象に加えて解決（`segmentEastKmContribution`）。
探索は経路上の全通過駅で「ここで降りたら」の運賃を評価するため、
終端には区間が閉じる前の中間駅も含まれる。

### 既知の限界（すべて安全側＝過大評価にしかならない）

- `lineId` は station.tsv 由来の内部ID。グラフ再生成で振り直される可能性があるため、
  再生成時は `EAST_KM_EXCLUDED_LINE_IDS` の値を要確認。
- `isEligibleExclusionName` は「東京都区内」を山手線（lineId `11302`）の駅名集合で
  近似している。品川・東京は山手線の物理ループ上にあるので規則の文言
  「品川・東京〜山手線内の各駅」とは自然に一致するが、東京都区内には
  山手線ループ上にない駅（中野・亀戸・金町など）も含まれ、それらは集合に入らない。
  つまり本来の「東京都区内」より狭い。
- 東京都区内・山手線内の駅でも、`11301`/`11302` 以外の路線経由で東海道方面へ
  入った場合（例: 京浜東北線の蒲田）は除外が効かない。
- 横浜市内発（新横浜〜熱海が新幹線経由扱いになる規則）は未対応。横浜は
  どちらの駅名集合にも含まれないため除外が発動せず、横浜→名古屋などは
  JR東日本分の加算額だけ高く見積もられる可能性がある。
- 除外区間の後に通常区間が混在する場合、除外区間分の距離も加算額に含めてしまう
  （`segmentOnlyExcludedLines` のラチェットによる近似）。

## 3. 探索の停止性

`next.fare`（今降りた場合の運賃）は override により非単調なので、これで枝刈りすると
「区間の途中は予算超過だが override で安くなる終点」を取りこぼす。代わりに
`confirmedFare`（確定済み区間の合計。経路に沿って非減少）に区間の下界を足した値で刈る。

停止性は「区間を伸ばせば下界が単調に増加して予算を超える」ことには依っていない
（下界は override anchor の場合に事業者単位の最安値で頭打ちになりうる）。
下界が常に 0 以上なので `confirmedFare <= budget` が保たれ、`confirmedFare` は
整数運賃の和で budget が有限なので取りうる値が有限個しかない、という理屈で停止する。

## 4. 未解決の課題

- 私鉄相互直通（例: 横浜→和光市）で実運賃より約30%高く出る。原因未特定。
- 予算10,000円での探索が約3〜4秒かかり、目標の1秒に未達。

## 3. 運賃計算（lib/fare/calculator.ts）の補足

`calculator.ts` 側に書ききらなかった論証をここに置く。

### lowerBound が返す下界の根拠

探索は「この事業者・この距離なら、この先どう乗り継いでも これより安くならない」額を
枝刈りに使う。`fromName` を渡すと下界を締められる。

- `fromName` がその事業者の特定運賃（override）の駅ペアに**一度も登場しない**場合、
  その区間はどの駅で降りても override を引けない。したがって距離表の運賃がそのまま
  有効な下界になる。距離表は km について単調非減少なので、下界も単調。
- `fromName` を渡さない、または override に登場する駅（anchor）の場合は override が
  効く可能性がある。距離表の運賃と、その事業者の override 最安値の小さいほうを返す。

後者では**下界が override の最安値（多くは初乗り）で頭打ちになり、km について
単調増加しなくなる**。富山地方鉄道のように全駅ペアを override にすると、
その事業者の中では距離による枝刈りがほぼ効かなくなる。

停止性はこの単調性ではなく、budget が有限で運賃が整数であること、および
`ParetoEntry.totalKm` が支配次元に入っていて rail の閉路を1周するたびに
真に増えることに依っている。

### isOverrideAnchor が探索を軽くする理屈

override は「区間全体の始点・終点」の駅ペアにしか適用されない（途中駅ペアには効かない）。
そのため、区間の起点がどの override ペアにも登場しない駅である限り、その区間は
どこで降りても override を引けず、**起点駅を区別する必要がない**。探索側はこれを使って
状態をマージし、状態空間の爆発を防いでいる。

裏返すと override を増やすほど anchor が増えて状態数も増える。全ペアを override に
した事業者（富山地方鉄道 2211ペア、しなの鉄道 435ペア）ではその事業者の全駅が
anchor になる。

### 区間運賃（fare-zones）と起点のまとめ方

JR西日本の「大阪附近の電車特定区間」のように、発着の両駅が区間内なら事業者の表の
代わりに安い表を引く区間がある（`data/fare-zones.json`、判定は `calculator.estimate`）。
区間内の起点からの運賃は着駅しだいで安い表になるので、区間外の起点とは将来の運賃が
違い、上の理屈で "" にまとめてはいけない。まとめると、同じ距離なら区間外の起点が
区間内の起点を支配して消し、安い運賃を取りこぼす。

一方、区間の表も距離だけで決まるので、区間内の起点どうしは区別しなくてよい。
そこで起点のキーは「override の anchor ならその駅名 → 区間内なら `zone:<id>` →
それ以外は ""」の3段にしている（`reachable.ts` の `originBucketKey`）。

下界は、発駅が区間内なら区間の表で取る（区間の表は全距離で事業者の表以下）。

### 地方交通線だけの区間（FareRule.localTable）

JR北海道・東日本・東海・西日本は、乗車区間がすべて地方交通線なら、地方交通線用の
別の表を営業キロで引く。幹線を1駅でも含めば、地方交通線の営業キロを換算キロ
（約1.1倍、`GraphEdge.fareKm`）にして幹線の表を引く。

探索は区間ごとに `segmentAllLocal`（地方交通線の辺だけで来たか。true→false のみ）と
その営業キロ `segmentLocalKm` を持つ。地方交通線の辺は「fareKm が営業キロより長く、
事業者が localTable を持つ辺」で見分ける。

`segmentAllLocal` は bucket のキー（flags の4ビット目）に入れる。地方交通線だけの
状態は換算キロが長くても安いことがあり（換算キロ19.8kmの地方交通線経由150円と、
19kmの幹線経由200円）、同じ bucket で距離を比べると幹線経由の状態が安い状態を消す。
地方交通線だけの bucket の中では換算キロ＝営業キロ×1.1なので、totalKm で比べて
よい。

下界は、区間が地方交通線だけなら幹線の表と地方交通線の表の安いほう。そのまま
進めば地方交通線の表、幹線に入れば距離が伸びて幹線の表で今の額以上になるため。
本州の7〜10kmのように地方交通線の表のほうが高い帯もあるので、min を取る。

既知の限界:
- JR本州3社をまたぐ通し運賃では地方交通線を区別しない（換算キロで基準額表）
- 表の範囲外（本州の基準額は200km、JR東日本は加算額表が73kmまで）は換算キロで幹線の表
- 幹線と地方交通線を合わせて営業キロ10km以下なら営業キロで幹線の表を引く規則は未対応
  （換算キロで引くので高めに出る側）

### JR本州3社の通し運賃

JR東日本・東海・西日本をまたぐ乗車は、会社境界で運賃を分割せず
「基準額（総営業キロ）＋ 加算額（JR東日本区間の営業キロ）」で計算する（2026年3月14日改定）。
三島会社（北海道・四国・九州）と私鉄との境界は対象外で、従来どおり区間を確定して
初乗りからやり直す（三島会社は加算額表の数値が未確認のため）。

`estimateHonshuThrough` に渡す `eastKm` は、呼び出し側（`reachable.ts`）が
「東京都区内・山手線内〜東海道方面は東京(品川)〜熱海間を新幹線(JR東海)経由として計算する」
規則を適用した後の値。この関数自体は表を2回引くだけで、その特例の判定はしない。

下界（`honshuThroughBaseFare`）は基準額のみを返す。加算額は常に0以上なので、
これを下回ることはない。

### 特定都区市内・東京山手線内（data/special-cities.json）

JRの旅客営業規則 第86条（特定都区市内）と第87条（東京山手線内）による読み替え。
区域内の駅から中心駅経由で200kmを超える駅へは、区域内のどの駅から乗っても中心駅
から計算する（山手線内は100km超200km以下、中心は東京）。発着とも区域内なら中心駅
どうしで、これは中心駅どうしが200kmを超えるときだけ。区域は12（札幌・仙台・東京都区内・
山手線内・横浜・名古屋・京都・大阪・神戸・広島・北九州・福岡）。運賃は安くなるとは
限らず、発駅が中心駅より着駅寄りなら高くなる（赤羽→仙台は実際の338.6kmでは5,940円、
東京からの351.8kmで6,270円）。

区域の駅は `scripts/fare/build-special-cities.ts` が、規則の別表の「路線：A〜B間」を
線路上でたどって作る。中心駅からの距離は起動時にグラフから測る（`lib/fare/special-cities.ts`）。
fareKm はグラフを作り直すと変わるので、データファイルには持たない。距離の表は2つある。
1社の中の運賃には区域の会社の線路だけで測った表を、本州3社の通し運賃には3社を
またいで測った表を使う。

距離は駅名ではなく物理的な駅（groupId）を頂点にして測る。駅名を頂点にすると、同名で
別の駅がつながってしまう。武蔵野線と大和路線の三郷、東北本線と関西本線の大河原が
つながり、東京→仙台が104.6kmになっていた。計算機は駅名しか知らないので、同名で別の
駅がある駅名（本州3社では26、JR東日本の中では大久保・大沢・根岸）は距離の表から外す。
その駅では規則を使わない。

**距離の近似**: 乗車経路は分からないので、中心駅からの距離を
max(実際の距離 − 発駅〜中心駅, 中心駅〜着駅の最短距離) とする（`calculator.ts` の
`specialCityKm`）。前者は発駅から区域の外へ向かう経路に、後者は発駅が中心駅より
着駅寄りの経路に合う。着駅側は発着を入れ替えた式、発着とも区域内なら
max(実際 − 発駅側の半径 − 着駅側の半径, 中心駅どうし) で求める。

**探索の状態**: 運賃計算の発駅 `fareFromId` を持つ。通し運賃の間は、本州3社に乗り
始めた駅を会社境界を越えて持ち回る。区域内の発駅からの運賃は、同じ距離でも区域外の
発駅とは違うので、bucket の起点キーに `|city:<区域id>` を付けて分ける。ただし、残りの
予算で規則の最低運賃（minKm の運賃）に届かない区域は分けない。届かないなら予算内の
着駅はどれも通常の運賃になり、まとめても結果は変わらないため。

**下界**: 読み替えで距離は縮みうるので、3通りの読み替えそれぞれについて、この先
どこで降りても下回らない距離を出し、そのうち最小の距離で表を引く:
- 発駅側: max(km − 発駅〜中心駅, minKm)
- 着駅側: max(km − 区域の半径, 中心駅〜発駅, minKm)。発駅を含まない区域についてだけ見る
- 両方: max(km − 発駅〜中心駅 − 着駅側の半径, 中心駅どうし, minKm)

km が最短の minKm 以下なら、下界を緩める必要はない。読み替え自体も、km が
「minKm − その区域の半径」に届かなければ調べない。読み替えた距離は「実際の距離＋
区域の半径」を超えないため。探索で最も多い短い区間をここで素通りさせる。
規則を入れると探索は東京発1万円で約1.6倍遅くなる（1.7秒→2.8秒）。状態数は約1.4倍に
増える。安くなった分だけ予算内に届く状態が増えるためで、避けられない。

既知の限界:
- 区域内の発駅どうしは区域でまとめるので、発駅〜中心駅の違いは比べない。違いが効くのは
  遠回りの経路だけで、そのとき高めに出ることがある（取りこぼしなので過大評価の側）
- 着駅側の読み替えは発駅〜着駅側の中心駅の距離にもよるが、区域外の発駅の状態は
  まとめたまま（同上、過大評価の側）
- 通し運賃の加算額（eastKm）は、JR東日本の区域（東京都区内・山手線内・横浜・仙台）で縮んだ距離だけ
  引く。読み替えで伸びた分は足さない。東京〜熱海の除外は区域内の区間が混ざると効かない
  （名古屋→赤羽は ekitan の6,380円に対し6,450円。東京→赤羽が除外の判定を崩すため）
- 「区域を通過する場合は適用しない」などの例外、新幹線だけの駅は未対応
