# テスト条件 - fare-map

> qa-manual-istqb の手順で作成した。テスト条件は「何をテストするか」、テストケース（`test-cases.csv`）は「どうテストするか」。

## 文書情報

- 対象: fare-map（予算内で行ける駅を地図に出す Web アプリ）
- 版: main（`878bb1c` 時点）
- 作成日: 2026-10-12
- テストの根拠:
  - README.md
  - API の入力検証（`app/api/*/route.ts`）
  - `docs/search-design.md`
  - 旅客営業規則（特定都区市内・通し運賃・東京〜熱海の除外）
  - auto memory に残した過去の不具合
- 照合の正解（オラクル）:
  - 公式の運賃表
  - ekitan の少数の抜き取り（規約上、少数に限り、保存は一致・不一致だけ）
  - 規則から導いた関係（往復で同額、予算を上げても運賃は変わらない、など）

## 品質リスク

リスク = 起こりやすさ × 影響（各3段階）。高いものからテストを厚くする。

| ID | リスク | 起こりやすさ | 影響 | レベル | 根拠 |
|---|---|:-:|:-:|:-:|---|
| R1 | JR の運賃規則（特定都区市内・通し運賃・加算額・地方交通線）の誤り | 高 | 高 | 高 | この1週間で規則まわりの誤りが続けて見つかった（加算額の70円など） |
| R2 | 距離データの誤り（同名駅のワープ、営業キロの読み違い） | 高 | 高 | 高 | 東京→仙台が104.6km になった件、大宮→盛岡のワープ |
| R3 | 探索の取りこぼし（枝刈り・状態の統合で安い経路を失う） | 中 | 高 | 高 | 状態を統合する近似を複数入れている |
| R4 | 私鉄の運賃表の誤り | 中 | 高 | 中 | PDF からの抜き出しで行や帯のずれが過去にあった |
| R5 | 予算が大きいときの検索の遅さ | 高 | 中 | 中 | 予算1万円で3〜7秒 |
| R6 | 画面の状態遷移の不具合（読み込み順序、検索の重なり、エラー後の復帰） | 中 | 中 | 中 | 地図の読み込み前に結果が届くと点が出ない不具合が実際にあった |
| R7 | API の入力検証・レート制限・セキュリティヘッダ・XSS | 低 | 高 | 中 | 公開する Web アプリ |
| R8 | 表示の分かりにくさ（駅グループの代表名、徒歩ありの印） | 中 | 低 | 低 | 名古屋が「名鉄名古屋」として出る |
| R9 | 外部の地図タイルの障害 | 中 | 中 | 中 | tiles.openfreemap.org に依存 |
| R10 | モバイル表示 | 中 | 中 | 中 | ボトムシートは別の実装 |

## メモ

- 境界値の駅（東京からの距離）:
  - 200km の境界: 越後湯沢 199.2km、泉（常磐線）200.8km
  - 100km の境界: 湯河原 99.1km、倉賀野 100.6km
- 性質ベースのテスト（往復・予算の単調性・JR だけとの比較）は、正解の運賃を知らなくても誤りを見つけられる。乱数で選んだ駅の組で回す。
- 前提: 運賃は概算で、IC運賃・特急料金・乗継割引は対象外（README の範囲）。
